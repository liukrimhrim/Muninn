## Exit check (from the plan)

All deterministic evidence/history invariants pass; semantic cases are inspected independently where reference judgments exist, with unresolved disagreement visible. Measure actual authoring/correction/practice time. Mark the pilot's limits; do not call it a validated learning improvement.

## Deliverables

2. **Acceptance pack v1** — [`qualification/pack-v1.json`](../../../qualification/pack-v1.json): fresh material in more than one subject (none of it in the drafting/assessment prompts, the test fixtures or the design's prototypes), covering an invented association, a relationship with an applicability condition, a connected argument with joint constraints and a text-described procedure with separate action-selection and outcome-verification criteria, plus the source-contains-instructions challenge. Reference notes are prepared independently of any model output. Held-out assessment variants (fixed rubric, frozen responses with reference judgments and rationale) never enter an authoring or practice prompt.
3. **Live qualification harness** — `uv run python -m tests.qualify`: drafting through the real application commands and store, assessment of the held-out variants through the real assessment request and checks, and a reviewable Markdown report listing every substantive error, disagreement, abstention, editing time and prompt version. No quality percentage, ever. It runs live only when `ANTHROPIC_API_KEY` is set; `--scripted` proves the harness without a key.
4. **Real-browser qualification** against `tests.dev_server` (preview "muninn-ui-check"): typing, help, submission, refresh/resume, correction, later-check scheduling with the clock, export/restore and the progress views, plus a timed use of the progress view (O12/O13). Recorded in the Comments below.
5. **Pilot limits statement** — [below](#pilot-limits).

## Decisions

1. **"Not reachable" is a disposition of its own.** Where no command in this build can produce a case's situation (shared exact targets, saved reports, cross-goal exposure relevance, migrations from a released format, …) the ledger says so with the missing capability, instead of stretching an unrelated test to look like coverage. Each such case reappears in the limits below.
2. **The harness lives beside the dev server** (`tests/qualify.py`, `python -m tests.qualify`), not in the `muninn` package: it is a qualification tool, not application code. It drafts through `App` commands into one real store for the whole pack (so a false reuse proposal between unrelated materials is a visible finding) and assesses held-out variants through `evidence.assessment_request` and `evidence.check_assessment` without a store, because their fixed rubrics are pack data, not drafted exercises. It never retries a held-out assessment (the app retries a refused output once; the harness records the first answer so refusals stay visible).
3. **Reference notes and judgments are the pack author's**, frozen in `pack-v1.json` (its sha256 is printed in every report) before any model output for the pack existed. They are not a human reference; reviewing them is the first human step.
4. **Editing time is a human measurement.** The harness cannot observe it; the report names the drafted library, the reviewer edits it in the app, whose time ledger counts that as authoring, and writes the minutes into the report.
5. **Help from a view known open while an answer is written is help (W04, tracking §4).** Evidence derives it at read time from the exposures (`outside_views`), so a view closed later still turns the answer into helped practice, and Practice and Measurement read the same rule (M04): Practice treats it as helped practice (an independent check a day later), Measurement reports raw H/QH with the aid reason kept. A view with no known end leaves the raw judgment and makes the claim uncertain, as before. Consequence for slice 4's "too soon" test: an answer whose own draft was open while the learner opened the claims is now helped; the "too soon" path is exercised by an earlier answer in another tab (`tests/test_later_checks.py::test_an_answer_too_soon_after_another_answer_cannot_advance_the_check`).
6. **The assessor is told when an answer came** (the assessor protocol: "the caller supplies whether this is a later session"): first recorded answer, immediate (earlier practice of these goals in the same session) or later session. The packet text changed, so `assess-answer` is now v3 and `reassess-answer` v2; saved operations keep their own snapshot and version.
7. **Restore refuses to hide learning (compatibility §4 import rules and §5 recovery after new writes; C07, C19, C20).** An archive of the same library may replace the active store only when the store is an exact prefix of it (records and receipts); otherwise the restore is refused with a 409 and nothing is created or switched. Another library's archive is not compared (the previous store stays on disk, as before).
8. **A concern waiting for a later check closes on an eligible later success (P06)**: an owned, on-time, delay-eligible answer that shows the whole scope without help resolves it, with no extra check; for a recall goal the learner's own review closes it (any rating but "forgot"), so the rating command settles it too. Only that closing answer can reopen it: a correction or a re-rating after which it no longer meets the check. An error inside a concern waiting for a later check sends that same concern back to repair.
9. **The browser closes its answer-bearing views before it moves on** (navigation awaits the close; "Finish session" closes them before ending the session), so the normal flow cannot race into a false "helped" or save unmet needs as "a view may still be open". POST requests use `keepalive` only below 60 000 bytes: browsers refuse larger keepalive bodies, which made restoring any library above 64 KiB fail. Time on the "question this judgment" and review pages is recorded as `assessment_correction`, the ledger category meant for it.
10. **Progress views say what happened.** The session headline counts the later checks answered in the session and how many were met; "later recall not checked yet" is shown only when none was answered. A check whose due time came from a helped first answer is listed in the later-checks history (with its failure or replacement), without listing the first answer as an answer to it.

## Pilot limits

**Qualified, deterministically (scripted model, real store, commands, HTTP and a real browser):** saving, resuming, retrying and restoring one learner's library without model calls and without hiding later work; criterion-level judgments kept apart from help, misreads, omissions and unjudgeable parts; diagnosis, teaching and fresh checks with their caps and stops; corrections that replay schedules from occurrence order once; FSRS recall reviews and the 24 h / 7 day capability policy across real clock boundaries, with exposure deferrals and help from views open elsewhere; budgets and unmet needs; frozen tracking plans; time accounting that never invents time; progress views that write nothing and say what happened.

**Only deterministic (not yet shown with a real model):** that drafting keeps a source's claims, conditions and connections and adds nothing unsupported; that assessment judges by meaning (valid alternatives, shorthand, misreads, embedded instructions); that teaching and fresh variants are useful and fresh; that reuse proposals are right. The pack and harness are ready; the scripted proof says nothing about quality.

**Still needs live and elapsed-time evidence (human steps, ledger):** reviewing the pack's reference notes; the live harness run with its editing times; a live learner flow in a real browser on unauthored material; a genuinely elapsed later session; an uncoached learner reading the progress views (O12); declaring format 1 released before any migration work (C02–C05).

**Known gaps and unreachable cases:** exposure relevance is by exact goal (no `exposure-scope-1`); a correction releases a whole mixed draft; answers with unknown times can only arrive by import and are not qualified; no shared exact targets, saved reports, weak-unit flags, efficiency flags, analysis tools, curriculum pause, split/merge or requirement edits; no physical migration exists yet.

**Not claimed:** this is not a validated learning improvement, and no measured quality, accuracy or efficiency is claimed. Counts in reports are findings to inspect, never percentages; a second model's agreement would not be a reference. Prediction and learning-benefit gates (Design Baseline 1 § 5) remain closed.
