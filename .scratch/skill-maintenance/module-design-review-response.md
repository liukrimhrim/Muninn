# Response to the independent module review

Status: design revision, 2026-10-15. The user pointed to another agent's [eighteen-comment review](module-design-audit.md). This response checks those comments against the contracts and records the resulting changes. It preserves the original review. No application was implemented and no runtime test is reported as passing.

The reviewed proposal is commit `07ea642` on `codex/research/observability-campaign`; its earlier baseline is `0127a4f` on that same branch. The research checkout holds the canonical committed snapshots. Primary-checkout documents are working copies, compared with the research copy when saving a snapshot. Neither acyclicity nor counting all 27 record kinds proved field-level cohesion: the review exposed real ownership and recovery gaps.

## Disposition of every finding

“Accepted” means the written contract needed revision. It does not establish a production defect or an implementation fix. Qualified dispositions retain the valid concern without adopting an unnecessary or incorrect remedy.

| Finding | Disposition and revised contract |
|---|---|
| A01 Scheduling effects in `transition` | **Accepted.** Practice owns `schedule.resolution_rule` and per-target `check_effects`. Application `transition` only links before/after refs and coordination provenance. The [lifecycle resolver](learning-lifecycle-contract.md#correction-after-later-checks) retains permanent revocation and historical replay semantics. No new record kind is needed. |
| A02 Duplicate owner/extra | **Accepted.** [Attempt purpose](compatibility-design.md#3-portable-logical-records) is initial/clarification/verification/practice. Practice resolves each target's effective role from its offer and release/correction history. A single larger attempt can own A and be extra for B; no whole-attempt due/extra flag can express that correctly. Historical owner role alone does not override a subsequent permanent release. |
| A03 Claim-definition owner | **Accepted gap, qualified rationale.** Two callers selecting parameters is not inherently duplicated interpretation. But the permitted definitions and their owner were unspecified. [Evidence now publishes named/versioned claims](module-design.md#named-qualification-claims), validates parameters and owns evaluation. Practice still owns its delay policy; Measurement owns report populations/formulas and labels any distinct claim. Saved identities include parameters, so “24 hours” and “seven days” cannot silently share one meaning. |
| A04 Duration and lifecycle time | **Accepted.** Remove attempt/session `elapsed_ms` from the unreleased proposal. [Activity spans](../learning-observability/data-contract.md#3-occurrence-time-is-evidence-not-a-required-guess) retain measured duration; Measurement derives elapsed/effort summaries. Practice records session lifecycle facts, each payload owner applies the shared value validator, Evidence interprets learning order, and Measurement interprets duration/placement. An observed session start is not itself an effort calculation. |
| A05 Public records versus private implementation | **Accepted wording, qualified conclusion.** Portable records are public versioned data with one writer. The SQL layout, repositories and algorithms remain private even when their logical output is public. The archived FSRS state is also public portable data; its interpretation stays opaque to other modules. Public data does not make all implementation public. |
| A06 Ownership enforcement | **Accepted missing mechanism.** The [transaction section](module-design.md#shared-transaction-private-responsibilities) specifies import/access checks and negative canaries. There is no promised runtime module sandbox. A naive SQL text scan is insufficient for generated/shared access: inspect those paths and reject unsupported computed write targets instead of reporting a vacuous pass. Exact tooling depends on the selected language. |
| A07 Export/migration access | **Accepted clarification.** Application Workflows calls fixed owner export, staging/import, migration and validation functions. [Library supplies snapshot/transaction/integrity mechanics](compatibility-design.md#4-snapshot-and-export-format), without importing domains or interpreting their tables. Fixed wiring is enough; no dynamic serializer registry is required. |
| A08 Practice–Measurement coupling | **Accepted effect clarification; retain the read dependency.** Measurement needs historical practice scope/offer facts. Passing every view through the application would move the dependency without removing its meaning. Keep that read interface and acknowledge that corrected/unknown measured budget can change Practice's choice. Practice owns the policy; Measurement cannot request extra work solely to improve a sample. |
| A09 Low-coupling claim | **Accepted qualification.** The graph establishes layering and absence of import cycles only. Low coupling and cohesion remain objectives tested through M10's concrete change-locality experiments. The build-plan wording no longer claims those properties are already established. |
| A10 Hold versus failure | **Accepted.** A held Practice result is a valid committed outcome. A corrected assessment survives an unavailable scheduler with an explicit held schedule and retained prior due/state. Invalid writes or technical failures roll back; domain uncertainty does not. Unaffected targets still settle. |
| A11 Submit/operation crash gap | **Accepted.** For model assessment, one command saves submitted evidence, the submitted offer, the pending operation and receipt. [The model call follows commit](module-design.md#shared-transaction-private-responsibilities). This rule covers submissions requesting model assessment; a later human correction remains a separate existing command. Restore remains read-only; interrupted external work follows explicit retry. |
| A12 Atomicity test value | **Partly accepted.** Add crash/restart checks around submission, external work and acceptance. Keep the failure injection between Evidence and Practice: it verifies that application code actually shares one transaction and does not commit early/open a second transaction. A database guarantee cannot prove the application uses it correctly. |
| A13 Competing starts | **Partly accepted.** M05 now names two stale clients, different command IDs, resume versus explicit-extra outcomes and mixed target slots. Serialization alone does not implement unique ownership, correct conflict responses or immutable prospective assignment. Keep those assertions through the real application interface/store. |
| A14 Provider adapter | **Accepted.** One provider transport adapter belongs to Application Workflows. Content/Evidence own their packets and semantic validators. Provider transport changes need not create two adapters or a new top-level module. A controlled test adapter is retained for timeout/malformed-result behavior. |
| A15 Operation semantics | **Accepted clarification.** Application owns lifecycle, exact bindings and storage of the result. The relevant domain supplies its typed acceptance disposition and validated output refs. The coordinator cannot infer an accepted assessment from a successful HTTP/model operation. |
| A16 Checkpoint vocabulary | **Accepted ambiguity; avoid a record rename.** Use “achievement checkpoint” for the Practice award and “prospective condition boundary” for Evidence's `condition_checkpoint`. Keep the portable kind name and explain the difference; no behavioral or compatibility gain justifies changing every reference. |
| A17 Seven slice-one modules | **Accepted packaging clarification.** Seven logical responsibilities do not require seven packages/wrappers. Build the exercised paths through four domain packages, application/store organization and the normal web UI. Do not scaffold empty future features. Interface depth and locality determine whether further packaging earns its cost. |
| A18 Baseline and copies | **Provenance corrected; prior commit verified.** `0127a4f` belongs to the research branch, not the primary prototype branch. The proposal was already committed there as `07ea642`. The design now names the branch and reviewed commit. Snapshot verification compares working copies and committed files; it does not promise automatic synchronization or pretend untracked primary files are committed on that branch. |

## Cross-contract reconciliation

The [module design](module-design.md) describes the interfaces and owner rules. The [compatibility contract](compatibility-design.md#3-portable-logical-records) changes the actual payloads, while the [lifecycle contract](learning-lifecycle-contract.md#correction-after-later-checks) moves the resolver's durable decisions into schedule revisions. The [data contract](../learning-observability/data-contract.md#3-occurrence-time-is-evidence-not-a-required-guess) and [tracking contract](../learning-observability/tracking-contract.md#3-plan-creation-closure-and-changes) assign time/claim semantics explicitly. The earlier correction closure keeps its outcomes, with its field-ownership reference updated.

This is still an unreleased format proposal. There is no invented migration from a shipped learner library. When there is a released format, its data/meaning must be preserved through the existing versioned conversion and replay contracts. Named claims use the existing Algorithm value, not a new database, registry service or executable rule language.

## Cases the implementation must demonstrate

These are authored design traces, not executed tests. They refine M01–M10 rather than replacing integration checks with document assertions.

| Case | Input/action | Required observable result |
|---|---|---|
| V01 Mixed roles | Larger attempt owns target A but another offer owns B | One saved response with neutral purpose; Practice reports A owner/B extra. Only an eligible A review can advance its bound opportunity. |
| V02 Correction then release | Correction revokes an unsubmitted descendant for A; later offer revisions and a favorable correction follow | The schedule's effects keep A permanently ineligible for that offer identity. Other target slots and the saved answer survive; exact revision refs remain auditable. |
| V03 Claim agreement | Same answer, target, anchor, source, named claim and parameters are used by Practice and Measurement | Same per-requirement eligibility/reasons. A different delay is a different pinned claim, not a silent override; unknown rules/parameters cannot qualify. |
| V04 Invalid clock | A known hint was shown but wall-clock time fails; the attempt is submitted | Save the answer and known help with unknown time. No duplicate duration field is invented; independent qualification remains helped/uncertain as appropriate, and effort quality remains separate. |
| V05 Unavailable engine | Accept a real assessment correction while the pinned recall engine cannot run | Commit correction/projection and explicit held schedule together, preserve prior due/state as held history, and leave unrelated targets usable. Do not discard the correction or generate a rating. |
| V06 Transaction failure | Inject failure after Evidence contributes but before Practice finishes | Reopen the real store: the entire correction is absent or committed; no half-state. This must fail if the application mistakenly uses two independent commits. |
| V07 Submission crash | Terminate before submit commit, after submit commit/before invocation, and after acceptance commit/before response | Respectively retain prior draft; recover submitted answer plus pending operation; return the accepted receipt on retry. No orphan answer, duplicate assessment effect or hidden restore-time model call. |
| V08 Stale tabs | Two clients read the same revisions; one reserves; the other sends a distinct command from stale state | Real conflict response offers the existing draft. Explicit distinct work preserves its answer as extra on occupied slots, with no late endpoint assignment. |
| V09 Budget correction | Same Practice policy receives a corrected cost summary, then one with an unknown tail | Known correction may alter selected work. Unknown time is not treated as zero or a guaranteed fit. No task is added merely to improve the dashboard's sample. |
| V10 Import/export seam | Export one S while a new answer commits, then restore with network disabled | Fixed owner serializers/validators preserve all logical records, schedule effects, claim identities and receipt membership from S. Later records cannot leak in; no semantic callbacks write learning events. |
| V11 Forbidden access | Add an illegal repository import or foreign read/write, including a shared/generated helper path | The selected architectural check rejects the change. A missed path is an enforcement limitation to fix, not evidence of runtime isolation. |
| V12 Lifecycle versus domain result | Provider request succeeds but its assessment is malformed or fails domain validation | Operation records the outcome and owner rejection; no accepted assessment/progress is fabricated from transport success. |

The actual module import/access checks, transactional commands, provider recovery and locality experiments remain implementation qualification.
